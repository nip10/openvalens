# Issue #17 bounded backend slice

Reads canonical `health_event` and `metric_sample` rows, with tenant-scoped source/definition joins and provenance, preserving anchovy's canonical item, exact case-insensitive source-label/source-ID filters, UTC date-only boundaries and severity/confidence inference. Samples are separate records, never median-resolved. Stable occurrence-descending/ID-ascending pagination filters before slicing; cursors are ordering boundaries, not snapshot tokens under concurrent writes.

The source query's seven domain adapters are now backed by actual target rows: `consultation`, `imaging_study`, `cardiac_exam`, `weekly_review`, `insight`, `scheduled_event` and `daily_reminder`. `DomainTimelineReader` is a typed internal projection facade over those org-scoped tables; it does not pretend that the target's calendar facade reads recurring schedules (it reads flat `calendar_event` rows). `timeline.list` retains the anchor's aggregate `records:read` membership/RBAC gate. Schedules/reminders are organization-shared records in this aggregate, as in the source query; this is not a current-user-only reminders endpoint. Every source query includes the active organization predicate, and org identity never comes from procedure input.

Domain source-file/source-record labels, self-provenance/related refs, summaries, severity/confidence and review-state inference follow the actual anchor adapters. Scheduled items represent their stored **start date**, not expanded recurrence instances. Text date/timestamp columns lack format constraints, so domain candidates are filtered on normalized UTC occurrence after merge; no lexical timestamp truncation or per-source LIMIT can lose matching records. Invalid source dates retain the anchor's epoch fallback, not a fabricated current time.

Deliberate query differences from the anchor: domain text-date SQL prefilters and per-source candidate caps are not copied because they can omit UTC-offset timestamps or equal-time ID boundaries. Cursor pagination extends the anchor's limit-only response using its lexical ID tie-break (e.g. `:10` before `:2`). The boundary review is excluded before slicing rather than after the anchor's limited fetch, preserving correct `hasMore`. Latest-review selection still uses the anchor's stored `weekStart` text ordering; malformed/non-date-only review boundaries are not repaired. Link lookups reject inherited object keys instead of returning non-string prototype properties.

`changesSinceReview` preserves the source endpoint's occurrence-window semantics: latest org weekly-review `weekStart`, otherwise seven UTC days, summarized over the returned page. The boundary review itself is excluded **before pagination**, so it cannot consume a page slot or falsely signal more results. It is **not** a mutation diff: there is no metric `updatedAt`, tombstone or persisted review snapshot. Historical late imports and edits outside the window are not represented. No fabricated deletions.

Provenance inserts validate and share-lock both referenced IDs in a transaction, using org predicates. Only existing canonical/raw-artifact tables are supported. Projection pseudo-tables are rejected; metadata cannot be persisted by this schema and is rejected by the repository. API inputs reject org/user/metadata overrides and writes require `records:write` with membership; one `RECORD_CREATED` audit is emitted after success, without payloads.

### Recurrence management (Issue #17 — bounded slice)

Pure helpers in `recurrence.ts` compute retention windows (`buildRetentionWindow`) and resolve dedupe decisions (`dedupeDecision`). There is **no default clinical retention**: the anchovy source only expires raw ingest payloads, never canonical `metric_sample` history. `buildRetentionWindow` and the repository's `pruneMetricSamples` require an explicit `retentionDays` and throw `RetentionPolicyRequiredError` (before any read or delete) when it is missing. `policyForMetric` returns `retentionDays: null` unless one is supplied; that value is a description, not authorization. IANA timezones are validated via `Intl.DateTimeFormat`; `retentionDays` must be an integer in `[1, 3650]`.

The actual schema enforces `UNIQUE(organization_id, dedupe_hash)`. Valid same-org same-hash duplicate sets cannot exist; `applyDedupeForMetric` therefore validates registered active catalog membership and returns zero without scanning/deleting samples. Distinct hashes, sources or equal timestamps are not inferred duplicates. The pure pairwise/cluster helpers do not override this DB constraint.

The API router mounts `metricRetentionPolicy` (records:read) and `runMetricDedupe` (records:write, audits one `RECORD_DELETED` / `metric_dedupe_applied` row; best effort). `runMetricRetention` stays mounted but is **disabled**: it always returns `PERMISSION_DENIED`, never reaches the repository and writes no audit. A caller-supplied `retentionDays` is not approval; pruning is only reachable through the trusted-server maintenance seam below. Strict inputs reject org/user overrides. Unknown taxonomy/unregistered/inactive metrics reject before deletion. Each prune deletes at most 100 samples by default (configurable bound 1000), retaining referenced samples rather than orphaning provenance or diagnostics.

### Server-only maintenance seam (not activated)

Import `createMetricMaintenanceRunner` and `isMetricMaintenanceDue` from `@openvalens/health-record/scheduler` (the existing wildcard package export). No cron route, background registration, all-org client query, schema/migration, cadence framework, `recurrence_run` or `lastRunAt` is added. A trusted server supplies one `MaintenanceScope`, a repository, a redacting audit callback, an explicit `now`, and a `dueAt` instant. Identity is not input: strict payloads reject organization/user overrides and PHI fields. The future integration must enforce membership plus `records:write` for any client-triggered invocation; this internal module is not an authorization middleware. Tenant enumeration belongs to the trusted server.

`now >= dueAt` is due, including equality; future instants return `not_due` without maintenance/audit. There is no implicit clock, DST calendar math or persisted schedule tracker. The caller must advance its external due state after success. Retention is **off when `retentionDays` is absent**: there is no call to prune, and no default window exists to fall back to. An explicit integer `[1, 3650]` additionally requires a trusted `authorizeRetention(scope, policy)` callback to return true; absent/denied authorization rejects before DB maintenance or audit. This is a policy injection point, not a built-in legal/clinical approval system. `maxDeleteCount` is `[1, 1000]`, default 100, with stable oldest-first/ID ordering and an inclusive retained cutoff (`sampledAt < now - days * 24h` is eligible).

One repository transaction combines the existing dedupe/prune implementations. A non-blocking transaction advisory lock keyed by tenant returns `busy` for overlapping cooperating maintenance workers. It is not an ingest lock, standalone API lock, durable idempotency key or exactly-once tracker; retries with unchanged due state can run/audit again. PostgreSQL hash collisions may conservatively produce a false busy. Candidate sample update locks and `SKIP LOCKED` bound the delete set; new ingest can occur between statements and is not guaranteed to be represented. Maintenance transactions run at `READ COMMITTED`, and the `DELETE` statement re-checks both provenance directions and `ingestion_error` references under its own fresh snapshot, taken after the candidate row locks are held. A reference committed after the candidate snapshot but before the lock is therefore still seen, and that sample survives. References that arrive after the lock either wait (repository provenance writer share lock, `ingestion_error` composite FK key-share lock) and then find the sample gone, or fail the FK; they cannot leave a dangling row. Guarantee limit: this does not hold if `pruneSamples` runs inside a caller transaction at `REPEATABLE READ`/`SERIALIZABLE`, which is why the repository opens its own `READ COMMITTED` transaction. Direct polymorphic `provenance_link` SQL writers that skip the share-lock validation have no guarantee.

Deletion preserves samples referenced in **either direction** by `provenance_link` (which has no sample FK), and by `ingestion_error` (whose single-column SET NULL FK coexists with a composite immediate FK). It does not delete links/errors or modify provider connections, ingestion batches, health events, domain records or raw artifacts. Reference/FK races can fail and roll back rather than silently destroy provenance. Legal holds, approved clinical policy storage and review/audit-history retention still need design before production deletion.

After commit, the runner attempts one typed `METRIC_RECURRENCE_RUN` summary through its injected writer; there are no nested standalone audits. Only taxonomy code, run instant, counts and explicit bounds are included, never sample values, metadata, hashes, IDs or clinical payloads. A null audit result is surfaced as `auditWritten: false`; audit persistence and mutations are not atomic. Integrators should pass `event => writeAuditLog({ db, ...event })` and monitor failures, not raw-insert audit rows.

Source comparison: anchovy has **no `recurrence.ts`**. Its `run-cron-orchestrator.ts` authenticates a cron secret, reclaims/claims one ingestion job, runs it, and invokes raw-payload purge in `finally`. `raw-payload-purge.ts` processes at most 25 expired raw artifacts/mobile chunks and purges payloads using stored retention expiry; it is not clinical sample deletion. `persist-canonical-records.ts` normalizes Health Connect intents, uses source-specific hash fields (including raw records) and persists canonical metric/event records. The target's existing typed ingest/hash surface is not the full source provider/orchestrator pipeline. Production cron, provider adapters, raw-payload purge integration and full ingestion activation remain deferred.

Remaining dependencies: taxonomy seeding/normalization, source preferences/priority resolution, interval helpers, ingest/canonical projection wiring and mutation-history tracking (not source review-window behavior). Direct blood-panel/marker, DEXA/body composition, weight, workout, medication/supplement-change and flat `calendar_event` adapters are **not in the anchor's timeline-query adapter set** and are not invented here. Such records appear only through existing canonical ingest rows or the supported schedule/reminder projections; there is no fabricated medication-change table or weight median step. All seven actual source domain adapters are implemented, not left as empty mocks.

### Reference links and unresolved target APIs

`timeline-links.ts` ports the source's pure link resolver and label formatter. It imports no UI/router/API dependencies. Preserved paths are `/blood` and `/blood/:id`, `/body`, `/cardiac`, `/imaging`, `/reports/weekly`, `/calendar`, `/records/timeline`; **none of these dashboard routes currently exist in target web routes** (only index/login/auth-dashboard routes are present). Returned hrefs express anchor compatibility, not target navigation completion. `consultation` and `insight` refs deliberately resolve to `null` as in the source, even though API record readers exist.

Target APIs already expose `clinical` blood/cardiac/imaging/consultation readers, `body` readers, `coach.listInsights/getInsight` and `timeline.list`. `plans.calendar.listEvents` reads `calendar_event`, not `scheduled_event`. No dedicated scheduled-event, weekly-review or daily-reminder read/detail facade was found in the target API routers; timeline projections read those actual tables via the org-scoped domain facade. These reference/detail APIs, target navigation and recurrence management remain unresolved and are outside this backend slice. Link-only mappings for legacy body/blood tables do not assert timeline adapter coverage.

Scaling gap: full org candidate scans ensure correctness for derived filters/cursors but are not suitable for massive tenants. SQL keyset/filter pushdown, bounded provenance fetches, snapshot consistency and suitable indexes require follow-up. No performance claim is made.
