# Rewrite nine tickets around verified constraints

Most of these nine tickets describe the right features, but several rest on facts that were false or out of date as of 2026-10-02, and a few of those errors would cause real harm if built as written. Four failures matter most. **Wearable APIs are not "free and well-documented"**: Garmin has paused new developer applications, and the Fitbit Web API shuts off on **2026-10-30**. The exercise dataset named in #93 is **not public domain**: its GIFs are © Gym visual, and shipping them would infringe copyright. The **default AI model `claude-sonnet-4-20250514` was retired on 2026-06-15**, so the server's default configuration fails today. And the cycle and body-diagram tickets encode physiology that the evidence contradicts: fixed calendar phase windows, "MacroFactor-style" macro deltas that MacroFactor does not offer, and a 30/70 upper/lower fat-loss split that someone made up. The maintainer's product decisions on all nine tickets hold up against the evidence. Where the evidence matters is in how they are built. Wearables should come through the existing Health Connect/HealthKit companion first, with server-side adapters only for providers whose developer programs let an individual register (Oura, Withings, Polar, Whoop). OIDC should go through Better Auth's `genericOAuth` with sign-up and implicit linking turned off. AI should use `@ai-sdk/openai-compatible` and should not depend on local servers handling tool calling well. i18n needs a Hermes `Intl.PluralRules` polyfill before any plural renders correctly on mobile. The exercise catalog should come from wger, which is AGPL and CC-licensed. The body map should show training volume and measured regional DEXA values, never fat loss inferred from total weight.

## Wearables arrive through the phone first, and through the cloud only where individuals can register

The cloud API landscape changed sharply in 2026. **Garmin staff confirmed that "new access requests are temporarily paused"** while the Connect Developer Program is updated, and gave no reopening date ([Garmin Forums](https://forums.garmin.com/developer/connect-iq/f/discussion/434798/cannot-access-developer-program-application-form-under-construction)). Even before the pause, applicants had to be a registered legal entity with a public website and privacy policy ([Open Wearables Garmin docs](https://openwearables.io/docs/providers/garmin-api-integration)). The unofficial route is no better. In March 2026 Garmin added Cloudflare TLS fingerprinting, and `garth` was deprecated with its final release on 2026-03-28 ([garth](https://github.com/matin/garth); [python-garminconnect #439](https://github.com/cyberjunky/python-garminconnect/issues/439)). Fitbit is in worse shape. Google ended support on 2026-09-30, **switches the Web API off on 2026-10-30**, and points developers to the Google Health API, whose v4beta public preview began only on 2026-10-01 ([Google Health API release notes](https://developers.google.com/health/release-notes)). Existing Fitbit tokens do not migrate, so every user must consent again ([Terra](https://tryterra.co/blog/fitbit-api-shutdown-september-2026-migration)). Suunto says plainly that it does "not provide this for personal use" ([Suunto API Zone FAQ](https://apizone.suunto.com/faq)), and Samsung Health exposes only an on-device SDK that needs partner approval ([Samsung](https://developer.samsung.com/health/data/guide/app-verification.html)).

Four providers remain viable for a self-hoster who registers their own credentials, the pattern Home Assistant uses for Fitbit ([HA #45291](https://github.com/home-assistant/home-assistant.io/issues/45291)). **Polar AccessLink** lets any Flow user create a client, scales its rate limits with users (500 + 20×users per 15 minutes), and supports webhooks or pull ([Polar](https://www.polar.com/accesslink-api/)). **Withings** allows 120 requests/minute per app and sends a notification callback when new data is ready ([Withings](https://developer.withings.com/developer-guide/v3/data-api/notifications/notification-overview/)). **Whoop** caps development mode at 10 members, which is plenty for a household, and requires signed webhooks answered within about one second ([WHOOP](https://developer.whoop.com/docs/developing/getting-started/); [webhooks](https://developer.whoop.com/docs/developing/webhooks/)). **Oura** retired personal access tokens in December 2025, so it is OAuth-only now, and its refresh tokens are single-use ([oura-mcp](https://github.com/HalmSascha/oura-mcp); [stethoscope.js](https://stethoscope.js.org/docs/integrations/oura-ring/)). Strava also works in "single-player mode", but its API agreement says data may not be used "in artificial intelligence models or similar applications" ([Strava press](https://press.strava.com/articles/updates-to-stravas-api-agreement); [Strava docs](https://developers.strava.com/docs/getting-started/)). That makes it a poor fit for an app with AI review unless every Strava-sourced record carries an AI-excluded provenance flag.

The phone covers more than the ticket assumes. Garmin, Oura and Whoop already write steps, heart rate, sleep, workouts and SpO2 into Health Connect and Apple Health. What gets lost is HRV and the proprietary scores: Readiness, Recovery and Body Battery ([sensai.fit](https://www.sensai.fit/blog/wearable-apple-health-integration-what-syncs-oura-whoop-garmin); [Constant](https://trainconstant.com/blog/whoop-apple-health)). These sync matrices come from secondary blogs and change over time. Taken together, this supports the narrow-integrations stance from the self-hosting research: **v1 ingests through the companion, and #60 becomes an adapter framework whose first targets are Oura and Whoop**, the providers whose cloud data adds the most beyond what reaches the phone. Commercial aggregators do not fit. Terra starts at $399/month billed annually and would sit in the PHI path as a processor ([Terra pricing](https://tryterra.co/pricing)). The MIT-licensed Open Wearables project is worth studying for adapter code ([Open Wearables](https://openwearables.io/compare)). The adapter framework itself needs several things the providers' terms require or imply: encrypted, org-scoped token storage; a locked atomic refresh to survive Oura's rotating tokens; handlers for deauthorization and `*.deleted` events that quarantine provider-sourced rows; Polar's de-register call on disconnect; and polling fallbacks for self-hosters with no public HTTPS ingress. Before committing to Google Health API, someone needs to answer an open question: does production use of Google's health scopes require app verification or a CASA assessment that an individual cannot pass?

## OIDC and AI both need conservative defaults, because PHI raises the cost of every mistake

### One env-configured OIDC provider that never creates accounts on its own

Better Auth's **`genericOAuth` plugin** is the right fit for "local accounts plus one generic OIDC provider." It needs only `providerId`, `clientId`/`clientSecret` and a `discoveryUrl`. When discovery exposes `jwks_uri` it verifies ID tokens, and PKCE is on by default ([Better Auth Generic OAuth](https://www.better-auth.com/docs/plugins/generic-oauth)). The heavier `@better-auth/sso` plugin targets runtime, DB-registered, per-organization IdPs, which v1 does not need ([Better Auth SSO](https://www.better-auth.com/docs/plugins/sso)). For invite-only registration, set **`disableSignUp: true`** so that only existing users can authenticate through OIDC. An invite then becomes the point where an IdP identity is bound by `iss`+`sub`, and the first-user bootstrap stays a local magic-link account so a misconfigured IdP can never become the instance owner. This is stricter than peer apps. Immich's `autoRegister` and Grafana's `allow_sign_up` both default to true ([Immich](https://docs.immich.app/administration/oauth/); [Grafana](https://grafana.com/docs/grafana/latest/setup-grafana/configure-access/configure-authentication/generic-oauth/)), and Gitea users complain that account linking cannot be separated from open registration ([gitea #27709](https://github.com/go-gitea/gitea/issues/27709)). A health app should not inherit those defaults. Role mapping from IdP claims should also stay out of v1.

The main takeover risk is linking accounts by email. Two 2026 advisories show how this plays out in Better Auth. GHSA-g38m-r43w-p2q7 covered implicit linking onto an unverified local account and was fixed in 1.6.11 ([GitHub Advisory](https://github.com/advisories/GHSA-g38m-r43w-p2q7)). GHSA-qq9h-g4jm-xgf3 covered magic-link pre-account hijacking in 1.1.3–1.6.21 and 1.7.0-beta.0–beta.9 ([GitHub Advisory](https://github.com/advisories/GHSA-qq9h-g4jm-xgf3)). **The pinned 1.7.5 sits outside both ranges.** GitHub's database currently lists nothing affecting 1.7.5. A third advisory cited by a third-party issue tracker does not resolve on GitHub and should be left out of the ticket. The underlying class of attack is still real: nOAuth showed that a mutable, unverified `email` claim lets attackers merge into victims' accounts ([Descope](https://www.descope.com/blog/post/noauth)). Better Auth's warning on `trustedProviders`, that it "may increase the risk of account takeover", applies here ([Users & Accounts](https://www.better-auth.com/docs/concepts/users-accounts)). Set **`disableImplicitLinking: true`** and offer an explicit "Connect OIDC" action from a signed-in session. If self-hosters want email trust, it can be an opt-in env flag that is off by default.

On mobile, Better Auth's Expo flow opens the system browser and returns through the app scheme listed in `trustedOrigins` ([Better Auth Expo](https://www.better-auth.com/docs/integrations/expo)). The docs show this only for `signIn.social`, so a spike must confirm that `signIn.oauth2` gets the same deep-link handling. Immich's HTTPS "mobile redirect" route is the fallback for IdPs that reject custom schemes ([Immich](https://docs.immich.app/administration/oauth/)). Apple's Guideline 4.8 requires an equivalent privacy-preserving login only when an app uses "a third-party or social login service" for the primary account. It exempts apps using "your company's own account setup" and existing enterprise accounts ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)). Several things keep the residual risk low: magic link stays first-class on iOS, the app hard-codes no Google or Facebook buttons, and the review notes explain that OIDC points at the server owner's own IdP. No Apple precedent specific to self-hosted OIDC was found. Passkeys (`@better-auth/passkey`) are a reasonable addition with `requireSession: true`, so they cannot bypass invites ([Better Auth Passkey](https://www.better-auth.com/docs/plugins/passkey)). Native passkeys bind to the instance's domain, though, and one App Store binary cannot list every self-hoster's domain in its associated-domains entitlement. Ship passkeys on the web first.

### Anthropic plus "any OpenAI-compatible endpoint" means designing for weak tool calling

The default model is broken today. **`claude-sonnet-4-20250514` was retired on 2026-06-15**, and `claude-sonnet-4-5-20250929` retires on 2026-11-30 ([Anthropic deprecations](https://platform.claude.com/docs/en/about-claude/model-deprecations)). The current lineup includes Claude Sonnet 5.5 (`claude-sonnet-5-5`, $2/$10 per MTok, retirement not sooner than 2027-09-28). Haiku 4.5 retires no sooner than 2026-10-15, so it is a poor long-lived default ([Anthropic models](https://platform.claude.com/docs/en/docs/about-claude/models/overview)). Move the default to `claude-sonnet-5-5` and remove any non-default `temperature`/`top_p`, which return 400 on Claude 4.7 and later. Confirm that the bundled `@ai-sdk/anthropic` version accepts the 5.x ids.

For the generic endpoint, use **`@ai-sdk/openai-compatible`**, not `@ai-sdk/openai`. Since AI SDK 5 the latter calls the Responses API by default, and most local servers implement Chat Completions well and Responses poorly ([AI SDK OpenAI](https://ai-sdk.dev/providers/ai-sdk-providers/openai); [OpenAI Compatible](https://ai-sdk.dev/providers/openai-compatible-providers)). Local servers handle tools unevenly. Ollama does not support `tool_choice` ([Ollama](https://docs.ollama.com/api/openai-compatibility)). vLLM needs `--enable-auto-tool-choice` and a parser flag, and even forced tool choice guarantees "a validly-parsable function call — not a high-quality one" ([vLLM](https://docs.vllm.ai/en/latest/features/tool_calling.html)). llama.cpp needs `--jinja` and warns that KV-cache quantization degrades tool calling ([llama.cpp](https://github.com/ggml-org/llama.cpp/blob/master/docs/function-calling.md)). So every AI feature must work without tool calling. Structured output should be validated with Zod, retried once, and otherwise return "could not parse", never invented values. Lab extraction from a local model should always go to user review. `AI_SUPPORTS_STRUCTURED_OUTPUTS` should default to false for compatible endpoints, and `AI_MODEL` should be required when the provider is not Anthropic. Model rankings for local tool calling (Qwen3 and Gemma 4 lead in secondary benchmarks) change monthly and come from low-authority sources. Ship a dated "tested models" matrix produced by an in-repo eval rather than a default local model id.

Consent copy should be generated from config. Health data is GDPR Art. 9 data processed under "explicit consent ... for one or more specified purposes" ([GDPR Art. 9](https://gdpr-info.eu/art-9-gdpr/)), so the consent screen should name the provider, the host from `AI_BASE_URL`, the purposes and the data categories. **Changing the provider or base URL should invalidate prior consent.** For hosted providers, the copy can state the verified terms: neither Anthropic nor OpenAI trains on API data by default, and both keep it for about 30 days, with longer retention for enforcement cases ([Anthropic retention](https://privacy.claude.com/en/articles/7996866-how-long-do-you-store-my-organization-s-data); [OpenAI](https://developers.openai.com/api/docs/guides/your-data)). For localhost or private IPs, it can say the data stays on the network.

## Plurals, Portuguese and health claims shape i18n and the launch surface

### Hermes lacks the Intl API that plurals depend on

The hidden blocker for #67 is that **Hermes documents no `Intl.PluralRules`, `Intl.Locale` or `RelativeTimeFormat`** ([Hermes IntlAPIs](https://github.com/facebook/hermes/blob/main/doc/IntlAPIs.md)). i18next has dropped its fallback since v24, so without a polyfill only English-style `_one`/`_other` keys resolve on native ([i18next](https://www.i18next.com/misc/json-format)). Every option therefore needs FormatJS's `@formatjs/intl-pluralrules` and `intl-locale` polyfills in the native bootstrap ([FormatJS](https://formatjs.github.io/docs/polyfills/intl-pluralrules/)). The ICU4X-backed `hermes-intl` is faster but at v0.1.x and requires RN 0.86+ ([hermes-intl](https://github.com/magrinj/hermes-intl)). Lingui 6 (ICU MessageFormat, about 2 kB core, build-time compilation, an official RN workflow) is the strongest technical fit for a shared web + Expo codebase ([Lingui](https://lingui.dev/introduction)). Choosing it means rewording the ticket to "no code change; release required". i18next with runtime JSON fits the original wording better. Paraglide has no official RN adapter. Add a unit test that runs pt and pl plural selection under Hermes so the polyfill cannot silently regress.

For translation management, the evidence points to **Hosted Weblate**. Its Libre plan is free for public projects ([Weblate hosting](https://weblate.org/en/hosting/)). It can require a DCO agreement and append `Signed-off-by: {{ author }}` to its commits ([Weblate licensing](https://docs.weblate.org/en/latest/admin/licensing.html)). Immich, the closest peer, uses it ([Immich translations](https://docs.immich.app/developer/translations/)). Crowdin's OSS license bars "commercial products related to the open-source project" and requires contributing to its global translation memory ([Crowdin](https://crowdin.com/page/open-source-project-setup-request)), which conflicts with a future hosted tier. The "community, unreviewed" label is well grounded. Under US ACA §1557, machine translations of patient-facing content must have human review ([npj Digit Med 2025](https://www.nature.com/articles/s41746-025-01944-0)), and LLMs have fabricated words in discharge instructions ([EthnoMed](https://ethnomed.org/resource/are-machine-translations-safe-to-use-for-patient-discharge-instructions/)). Use Weblate's reviewed state to drive the badge, and **fall back to English for safety-critical strings** (units, reference-range flags, dosing labels) until a reviewer approves them. Never translate analyte codes, units or medication names. Language, region formatting and clinical units should be three separate settings. mg/dL versus mmol/L depends on the lab, not the UI language. Hermes formats dates and numbers through platform APIs, so output differs between iOS and Android ([Hermes](https://github.com/facebook/hermes/blob/main/doc/IntlAPIs.md)). Unit-specific defaults per country still need a primary source before they are encoded.

### The launch surface must avoid the claims that make software a medical device

For #66, peers lead with Docker Compose. Immich calls it "the recommended method to run Immich in production" and labels its install script "[Experimental]" ([Immich](https://docs.immich.app/install/docker-compose/)). Mastodon keeps its marketing site in a separate repo ([joinmastodon](https://github.com/mastodon/joinmastodon)). A separate static landing site with **zero third-party requests** is the safe default. LG München (3 O 17493/20) awarded €100 damages over remotely embedded Google Fonts, because self-hosting the fonts was a free alternative ([KPMG Law](https://kpmg-law.de/en/google-fonts-warning-wave-massive-warnings-and-claims-for-damages-due-to-alleged-dsgvo-violation/)). The copy needs the most care. Under MDCG 2019-11, whether software is a medical device turns on intended purpose, and marketing claims count toward it. Rev.1 confirms that purely lifestyle or wellness purposes are not MDSW ([OpenRegulatory](https://openregulatory.com/mdcg/mdcg-2019-11); [Emergo](https://www.emergobyul.com/news/european-revision-primary-software-guidance-mdcg-2019-11-revision-1-small-changes-meaningful)). The FTC's Health Products Compliance Guidance applies to health apps and requires competent and reliable scientific evidence for claims ([FTC](https://www.ftc.gov/business-guidance/resources/health-products-compliance-guidance)). The FDA's General Wellness guidance was revised on 2026-01-06 ([Covington](https://www.cov.com/en/news-and-insights/insights/2026/01/fda-issues-revised-guidance-on-general-wellness-products)). The README and landing page should therefore say "record, organize, visualize" and never "detect, diagnose, predict, interpret". The pt-PT translation must keep that verb discipline. Apple requires one 6.9" iPhone screenshot set (1320×2868) per localization ([ScreenKit](https://screenkit.tools/specs/app-store-screenshot-sizes), secondary). Every screenshot, the docs, and any public demo should come from one deterministic `seed:demo` fixture with a PHI lint, never from a real account.

## Streaks and cycle tracking work when their worst failure modes are designed out

### Duolingo-style forgiveness is the evidence-backed half of the streak decision

The maintainer chose a Duolingo-style streak with freezes and repair. The evidence explains why forgiveness has to be central. In six experiments, Silverman & Barasch found that **a broken streak lowers continuation even when outside events caused the break** ([CU Boulder summary](https://www.colorado.edu/business/faculty-research/2023/04/19/or-track-how-broken-streaks-affect-consumer-decisions)). Duolingo's own data, which is not peer-reviewed and measures engagement only, shows retention "drops abruptly if a streak is lost". The same data reports that Streak Freeze cut churn by 21% among at-risk users and that two free freezes early in a streak help most ([Lenny's Podcast summary](https://www.getrecall.ai/summary/lennys-podcast/behind-the-product-duolingo-streaks-or-jackson-shuttleworth-group-pm-retention-team)). The underlying benefit is modest and temporary. A 16-RCT meta-analysis found gamification's physical-activity effect of g=0.42 fell to g=0.15 at about 14 weeks of follow-up ([Mazéas et al., JMIR 2022](https://www.jmir.org/2022/1/e26779)). These findings translate into specific choices. Grant freezes from day one. Count backfilled entries. Never send a notification that mentions a missed day. When a streak ends, lead with a cumulative non-resetting figure ("days logged this month") instead of the broken count, because highlighting the break is the demotivating step. Drop any "retention lever" health rationale from #90, since none of the evidence is about health outcomes.

The ED safeguards are well supported. Cross-sectional studies link calorie tracking to eating-disorder symptoms, mainly in people with existing body dissatisfaction ([Simpson & Mazzeo 2017](https://www.sciencedirect.com/science/article/abs/pii/S1471015316303646)). **73.1% of ED patients who used MyFitnessPal said it contributed to their disorder** ([Levinson et al. 2017](https://pmc.ncbi.nlm.nih.gov/articles/PMC5700836/)), and MyFitnessPal use predicted ED symptoms in men after controlling for confounds ([Linardon & Messer 2019](https://www.sciencedirect.com/science/article/abs/pii/S147101531830326X)). Hiding streaks under the self-declared ED exclusion and hide-numbers mode is the minimum. The exclusion should also suppress streak-related notifications and badges, not just the counter. No study tests streaks specifically as an ED risk factor.

### Cycle phases must be counted backward and labelled as estimates

Fixed calendar windows fail on the data. Across **612,613 ovulatory cycles, the follicular phase averaged 16.9 days with a 95% range of 10–30**, and luteal length ranged from 7 to 19 days even within 28-day cycles ([Bull et al., npj Digit Med 2019](https://www.nature.com/articles/s41746-019-0152-7)). The estimated-phase display should therefore anchor on the _next_ period. The luteal phase is roughly the last 12–14 days, so a phase becomes reliable only once that next period is logged. Before then, show it with explicit low confidence. Phase derivation should switch off entirely when a user sets hormonal contraception or "no natural cycle". The no-macro-adjustment decision is well grounded. A meta-analysis found the luteal RMR rise shrank to a non-significant effect in post-2000 studies ([Benton et al., PLOS ONE 2020](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC7357764/)). A 2026 review put it at **30–120 kcal/day, possibly within "day-to-day biological variability… or measurement error"** ([Hurtová et al., Front Physiol 2026](https://pmc.ncbi.nlm.nih.gov/articles/PMC13066135/)). **MacroFactor's own help centre says period tracking is "purely for personal reference"** ([MacroFactor](https://help.macrofactorapp.com/en/articles/17-track-your-period)). Overlaying periods on the weight-trend chart lets users see their own water-weight pattern without the app prescribing anything.

Regulation sets a clear outer boundary. Software that tells fertile from non-fertile days to prevent pregnancy is an FDA Class II device ([DEN170052](https://www.accessdata.fda.gov/cdrh_docs/reviews/DEN170052.pdf)), and Clue became a regulated device the moment it added a contraception claim ([MobiHealthNews](https://www.mobihealthnews.com/tag/clue-birth-control)). So OpenValens must never output a "fertile window" or "safe days". Reproductive data carries the heaviest enforcement history in consumer health: the FTC's Flo order ([FTC](https://www.ftc.gov/news-events/news/press-releases/2021/06/ftc-finalizes-order-flo-health-fertility-tracking-app-shared-sensitive-health-data-facebook-google)), Premom's $100,000 HBNR penalty ([WilmerHale](https://www.wilmerhale.com/en/insights/blogs/wilmerhale-privacy-and-cybersecurity-law/20230525-ftc-brings-second-enforcement-action-against-healthcare-company-for-violating-the-health-breach-notification-rule)), the 2025 jury verdict against Meta over Flo's SDK ([Healthcare IT News](https://www.healthcareitnews.com/news/jury-finds-meta-liable-reproductive-health-data-case)), and Washington's MHMDA, which requires consent kept apart from other agreements ([FPF](https://fpf.org/wp-content/uploads/2023/04/FPF-Legislation-Policy-Brief_-The-Washington-My-Health-My-Data-Act-Public-Version.pdf)). Self-hosting removes the SDK risk but not subpoena risk, and on shared instances it does not remove the risk of other members seeing the data. Alongside the decided separate consent and AI/coach exclusion, cycle data should be excluded by default from clinical/CSV/PDF exports, Telegram, email and telemetry. It should be invisible to other org members, deletable through a "turn off and erase" flow, and shown on screens with no third-party code. Import is straightforward. Health Connect offers `MenstruationPeriodRecord` and `MenstruationFlowRecord` behind a dedicated `READ_MENSTRUATION` permission ([Android](https://developer.android.com/health-and-fitness/health-connect/data-types)). Request that permission only after the user enables cycle tracking. HealthKit exposes only `menstrualFlow` samples, so iOS import must infer period intervals from flow ([Apple](https://developer.apple.com/documentation/healthkit/hkcategorytypeidentifier/menstrualflow)).

## wger supplies a lawful exercise catalog, and measured DEXA regions feed the body map

### Only wger's media is licensed for redistribution

The licence trap in #93 is explicit in the dataset's own LICENSE. The MIT grant covers "ONLY the code, tooling, dataset structure, and instruction text", and the media "is © Gym visual … Cloning this repository does not grant you any license to the media" ([LICENSE](https://github.com/hasaneyldrm/exercises-dataset/blob/main/LICENSE)). Gym visual forbids any redistribution ([Gym visual T&C](https://gymvisual.com/content/3-terms-and-conditions-of-use)). The repo's history was rewritten on 2026-07-08, and a copyright issue remains open ([Issue #3](https://github.com/hasaneyldrm/exercises-dataset/issues/3)). The obvious alternatives are no cleaner. The yuhonas/free-exercise-db maintainer says "I actually have no idea where the images are from" ([Issue #2](https://github.com/yuhonas/free-exercise-db/issues/2)), and users have traced some of them to ExRx ([Issue #13](https://github.com/yuhonas/free-exercise-db/issues/13)). Its upstream, wrkout, admits its images were "scraped off the internet" ([Issue #305](https://github.com/wrkout/exercises.json/issues/305)). ExerciseDB's GitHub repo contains only a README that points to paid RapidAPI plans ([repo](https://github.com/ExerciseDB/exercisedb-api)).

**wger is the clean source.** Its server is AGPL-3.0, matching OpenValens, and its data carries per-entry Creative Commons licences ([wger](https://github.com/wger-project/wger)). The live API on 2026-10-02 returned **916 exercises (763 CC-BY-SA 4, 132 CC-BY-SA 3, 21 CC0), 376 CC-BY-SA images and 78 videos**. It also has translations in Spanish (645), German (631) and French (584), and muscle assignments for 770 exercises ([exerciseinfo](https://wger.de/api/v2/exerciseinfo/); [language](https://wger.de/api/v2/language/)). Portuguese coverage is thin, so pt-PT exercise names will need community work. Build a one-time import job that copies wger JSON and images into OpenValens's own storage and keeps `license_author` for each entry, then serve them from the instance's own origin. The yuhonas JSON text (Unlicense, no images) can fill gaps in the taxonomy. Do not hotlink `raw.githubusercontent.com`. GitHub tightened unauthenticated limits there in May 2025 ([GitHub Changelog](https://github.blog/changelog/2025-05-08-updated-rate-limits-for-unauthenticated-requests/)), and every request would tell GitHub which exercise a user is viewing.

### The body map should show what was trained and what was measured

The physiology behind #94's 30/70 split does not hold. A meta-analysis of 13 studies with 1,158 participants found **localized training had no effect on localized fat (pooled ES −0.03, p=0.508)** ([Ramirez-Campillo et al., Human Movement 2022](https://hummov.awf.wroc.pl/A-proposed-model-to-test-the-hypothesis-of-exercise-induced-localized-fat-reduction,143162,0,2.html)). In a DXA study where participants trained one leg for 12 weeks, fat fell in the arms (−10.2%) and trunk (−6.9%) but not in the trained leg ([PubMed 23222084](https://pubmed.ncbi.nlm.nih.gov/23222084/)). Storing "per-region intensity snapshots" derived from scale weight would put fabricated anatomy into a PHI record. OpenValens does not need to invent anything, because **it already stores measured regional DEXA data** (`dexa_scan`/`dexa_regional`, with regions such as `right_arm` and `left_trunk` and measures `fat_pct` and `bmd`, exposed through `body.listDexaRegionals`). The measured-site layer should colour only the regions a scan actually reported, showing the scan date and source, and leave unscanned regions neutral. Optionally it can add tape-measure circumferences. The second layer is the one peers ship: weekly sets per muscle group, as in Hevy ([Hevy](https://www.hevyapp.com/features/muscle-group-workout-chart/)), and recovery recency, as in Fitbod ([Fitbod](https://fitbod.me/blog/muscle-recovery/)). It is computed from logged workouts through the catalog's primary and secondary muscle mappings. The two layers answer different questions and should stay visually separate.

On the rendering side, `vulovix/body-muscles` is Apache-2.0 with 89 left/right-split regions. Its regions map well onto DEXA's arm/leg/trunk sides, but its renderer calls `document.createElementNS` and therefore cannot run in React Native ([BodyChart.ts](https://github.com/vulovix/body-muscles/blob/main/src/BodyChart.ts)). It also has one release and four commits. **`react-native-body-highlighter`** (MIT, Expo-compatible, maintained, male/female, front/back, per-side intensity) is the safer runtime dependency for mobile ([repo](https://github.com/HichamELBSI/react-native-body-highlighter)), and its web sibling lives at `soroojshehryar/react-muscle-highlighter` ([repo](https://github.com/soroojshehryar/react-muscle-highlighter)). The durable design is a shared body-map package that exports region ids, display names and SVG path data, along with mappings from wger muscles and from DEXA regions to region ids. Thin `<svg>` and `react-native-svg` renderers consume it. Path data can be vendored from either library, provided Apache-2.0's NOTICE is preserved.

## Conclusion

Across these nine tickets, the errors come from three sources: ticket text copied from vendor marketing, from stale repo states, or from intuition. Several of the "facts" had changed only months earlier: Garmin's pause, Oura's PAT removal, the rewritten history of the exercise dataset, the model retirement. That argues for writing every external dependency into a ticket with a verification date and a primary-source link, and for a recurring check of model ids and provider programs. The Fitbit cutoff on 2026-10-30 and the Haiku 4.5 retirement window opening 2026-10-15 both fall within weeks of this report.

The evidence also points to a design principle the tickets did not state. Every feature that can display health information should show either something measured or something the user logged. It should never show a derived quantity that looks more precise than its inputs. Calendar-derived ovulation days, weight-derived regional fat, phase-derived macro targets and unreviewed translations of dosing labels all fail that test in the same way. The fix is the same each time: show the measured value with its provenance (a DEXA region, a logged period, wger's licence author), or label the derived one as an estimate. OpenValens's data model already supports this. Its regional DEXA tables and provenance fields are the reason the body map can be built honestly.
